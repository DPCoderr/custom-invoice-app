# Frontend conventions

## Goals

Frontend code should make the data flow visible:

```text
route -> query options -> API function -> response type
form -> Zod schema -> request mapper -> mutation -> query invalidation
```

Use TanStack Query for server state, TanStack Router for URL and route lifecycle, React Hook Form
for form state, Zod for client validation, and shadcn/ui primitives for presentation.

## Feature structure

Use feature-owned files rather than a global collection of unrelated API helpers:

```text
src/features/services/
|-- contracts.ts
|-- schema.ts
|-- api.ts
|-- queries.ts
|-- mutations.ts
|-- service-form.tsx
`-- service-select.tsx

src/features/invoices/
|-- contracts.ts
|-- schema.ts
|-- api.ts
|-- queries.ts
|-- mutations.ts
|-- mappers.ts
|-- create/
|   `-- create-invoice-form.tsx
|-- list/
`-- detail/
```

Shared infrastructure belongs under `src/lib`; reusable form adapters belong under
`src/components/form`; generated shadcn primitives stay under `src/components/ui`.

## Route files

Routes own:

- route identity and search/param validation;
- authentication/authorization guards;
- critical query preloading;
- pending, error, and not-found boundaries;
- page-level composition.

Routes do not own fetch implementations, large forms, tables, mock production data, or business
calculation.

```tsx
export const Route = createFileRoute("/_authenticated/invoices/")({
  loader: ({ context }) =>
    context.queryClient.ensureQueryData(invoiceListQueryOptions()),
  component: InvoiceListPage,
});
```

`src/routeTree.gen.ts` is generated by TanStack Router. Never edit it manually.

## Import aliases

- Use `#/*` for application-owned modules.
- Use relative imports within a small feature when it improves locality.
- Existing shadcn-generated files may retain `@/*`; do not churn generated UI files only to change
  aliases.
- Use `import type` for type-only imports.

## Shared API client

After `FND-004`, every application API function uses one shared client and relative URLs.

The client is responsible for:

- `credentials: "include"`;
- JSON request headers when a body exists;
- no body parsing for `204` or an empty response;
- parsing JSON and Problem Details once;
- distinguishing validation, authentication, server, and network failures;
- preserving an optional `AbortSignal`;
- never logging credentials or full sensitive responses.

Conceptual interface:

```ts
type ApiRequestOptions<TBody> = Omit<RequestInit, "body"> & {
  body?: TBody;
};

export class ApiError extends Error {
  constructor(
    message: string,
    readonly status: number,
    readonly errors?: Record<string, string[]>,
  ) {
    super(message);
  }
}

export function apiRequest<TResponse, TBody = never>(
  path: `/api/${string}`,
  options?: ApiRequestOptions<TBody>,
): Promise<TResponse>;
```

Do not catch a parsed `ApiError` and replace it with “Failed to connect.” Only fetch/transport
failures receive a network-specific message. Do not call `response.json()` twice.

## Contracts

- Keep hand-written request/response types in the consuming feature.
- Match the JSON names in [REQUIREMENTS.md](../REQUIREMENTS.md).
- Do not reuse a form type as an HTTP request merely because fields currently overlap.
- Use a mapper whenever dates, optional values, or form-only fields differ.
- Never include client-calculated total, owner ID, invoice number, seller snapshot, or storage key
  in `CreateInvoiceRequest`.

Example:

```ts
export type CreateInvoiceRequest = {
  issueDate: string;
  dueDate: string;
  customerName: string;
  customerEmail?: string;
  customerAddress: string;
  currency: "EUR";
  notes?: string;
  items: Array<{
    serviceId?: string;
    description: string;
    unitPrice: number;
    quantity: number;
  }>;
};
```

## Query keys and query options

Define keys centrally per feature:

```ts
export const serviceKeys = {
  all: ["services"] as const,
  list: () => [...serviceKeys.all, "list"] as const,
};

export const serviceListQueryOptions = () =>
  queryOptions({
    queryKey: serviceKeys.list(),
    queryFn: ({ signal }) => getServices(signal),
  });
```

- Use `queryOptions` so loaders and components share the same key/function.
- Preload data required to render the route.
- Pass the query signal to the API client.
- Set stale times deliberately; do not use `Infinity` for session data without an invalidation
  policy.
- Only a real `401` maps the current-user query to `null`. Network and server failures throw.

## Mutations

Mutation hooks live in the feature and own cache updates:

```ts
export function useCreateServiceMutation() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: createService,
    onSuccess: () =>
      queryClient.invalidateQueries({ queryKey: serviceKeys.all }),
  });
}
```

Forms may translate an `ApiError.errors` dictionary into field errors. Keep a root error for a
failure that does not map to one input. Prevent duplicate submissions while pending.

After login/register/logout, update or invalidate the current-user query before navigation so route
guards do not read stale session state.

## Forms and Zod

- Define one Zod form schema per use case.
- Infer form types from the schema.
- Use `zodResolver` with React Hook Form.
- Supply all controlled fields in `defaultValues`.
- Keep server validation authoritative even when the same rule exists in Zod.
- Render field errors next to their control and a root error for non-field failures.
- Use `useFieldArray` for invoice lines and stable generated keys for rendering.
- Require at least one invoice line and prevent removing the final line without replacement.
- Selecting a service prefills description and unit price but leaves them editable.

Do not store form-controlled dates in separate `useState` variables. The form is the single source
of truth.

### DateOnly mapping

The UI may use `Date` for a calendar control, but the request must send a date-only string:

```ts
function toDateOnly(value: Date): string {
  const year = value.getFullYear();
  const month = String(value.getMonth() + 1).padStart(2, "0");
  const day = String(value.getDate()).padStart(2, "0");
  return `${year}-${month}-${day}`;
}
```

Use local calendar parts rather than `toISOString().slice(0, 10)`, which can shift the day across
time zones.

## Money and totals

JavaScript `number` is acceptable for displaying and collecting MVP input, but the backend is the
authority. Frontend totals are previews only.

- Do not send preview totals.
- Format currency with `Intl.NumberFormat`.
- Keep `EUR` explicit in the MVP.
- Avoid equality comparisons on calculated floating-point previews.
- Display the server-returned total after creation.

## UI components and accessibility

- Prefer existing shadcn/ui primitives before adding a new component library.
- Keep domain behavior out of `components/ui`.
- Associate every label with a control.
- Use semantic links for navigation and buttons for actions.
- Do not use `href="#"` placeholders in completed flows.
- Preserve keyboard navigation and visible focus.
- Provide loading, empty, error, and success states for server-backed screens.
- Use Sonner to confirm successful mutations; do not rely on a toast as the only error detail.

Generated shadcn files may trigger broad lint rules. Fix accessibility at the usage site first; edit
the primitive only when the primitive itself is wrong and the ticket includes that scope.

## Localization

English is the initial locale. After `I18N-001`:

- put user-facing text in feature-scoped English resource files;
- use stable semantic keys, not the English sentence as a key;
- keep API error titles generic and map known validation fields to localized form labels;
- use the selected locale for dates and currency display;
- keep identifiers, routes, DTO properties, logs, and database values in English;
- do not add Dutch strings until the Dutch localization ticket begins.

The first localization ticket does not add a language switcher and does not add a PDF language to
the invoice contract.

## Tests

Prioritize:

- Zod boundary and cross-field tests;
- date-only mapper tests in positive and negative UTC offsets;
- API client tests for empty success, JSON success, validation Problem Details, `401`, `500`, and
  network failure;
- authentication cache/redirect behavior;
- invoice field-array add/remove/select/edit behavior;
- mutation invalidation;
- invoice list empty/error/success states.

Use Testing Library queries that reflect accessible names. Test behavior rather than shadcn
implementation details.

## Avoid

- hardcoded `http://localhost` API calls;
- duplicate `getUser` implementations;
- parsing one response body twice;
- converting all API errors to `null`;
- large route components containing fetch, form, and table logic;
- mock data in a completed production route;
- sending `Date` objects directly to a `DateOnly` backend;
- duplicating React Hook Form state in `useState`;
- editing generated route-tree output;
- adding invoice statuses or VAT fields before their post-MVP tickets.
